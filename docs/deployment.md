# AWS deployment package — prepared, not provisioned

Architecture: browser → HTTPS ALB (ACM certificate, HTTP→HTTPS redirect) → private ECS Fargate service (Gunicorn port 8000) → private RDS PostgreSQL. WhiteNoise serves public static assets bundled in the image. One database and shared sessions; no Redis or separate API. Do not run the production database inside ECS. No uploads are implemented; add authorized S3-backed storage before accepting business attachments.

`infra/ecs-task.json` is a parameterized task definition, not a provisioned network. `infra/render_task.py` renders ARNs/hostnames from environment variables and fails when required names are absent. It never takes actual secret values. 0.5 vCPU/1 GiB, two workers, is an initial measurement candidate, not an asserted capacity. Read-only root FS with writable `/tmp`; logs to CloudWatch; DB readiness at `/health/`. The health endpoint contains no business data and is exempt from HTTPS redirect for internal probes. Business paths require HTTPS in production.

## Gates before production

1. Confirm AWS Region, company isolation, operational QC policy, staff grants and wage recognition. Financial settlement remains disabled. Do not load real cross-company data while legal visibility is unresolved.
2. Verify RDS **17.11** is orderable in the chosen Region before provisioning:
   `aws rds describe-orderable-db-instance-options --engine postgres --engine-version 17.11 --region <region>`. Do not silently substitute another engine version.
3. Price the complete design using the AWS calculator for that Region. A preliminary small-team planning allowance is **USD 100–200/month** for one Fargate task, single-AZ RDS + storage/backups, ALB, one NAT gateway and modest logs/traffic; this is **not a verified current quote**. Multi-AZ DB/second task/extra NATs can materially increase it. Fargate-only cost understates the bill. A no-NAT design needs separately priced VPC endpoints and an SMTP/egress plan. No paid resources were created in this task; current regional pricing must be obtained before approval.
4. Create separate development/test/production DBs. Use private RDS subnets, no public endpoint, encryption, backup retention (propose 14 days pending owner approval), deletion protection. RDS security group accepts 5432 only from app/migration security groups. ALB accepts 443; app accepts 8000 only from ALB. Restrict admin/exec and deployment IAM.
5. The production task references `/run/certs/rds-ca.pem`. Include the verified current **AWS RDS CA bundle** in the release image before deployment, set ownership/readability, and verify `sslmode=verify-full` against RDS. This certificate file is intentionally **not fabricated or assumed present**. The current local image is not ready for that task until this step is complete. Trust/rotation needs a release procedure. Keep TLS verification enabled.
6. Supply Secrets Manager ARNs for Django key, DB password and SMTP credentials. Execution role gets narrowly scoped read/KMS access; task role has no AWS rights unless necessary. Application DB role gets only application DML/schema-read; use a separate controlled migration role for DDL. Local Compose user is intentionally broader for test database creation, not a production role.
7. Set DEBUG=0, exact hosts/CSRF origins and PUBLIC_BASE_URL. Keep secure cookies/HSTS. `TRUST_HTTPS_PROXY=1` is permitted only with network access restricted to ALB, which must sanitize client forwarding headers. Review real client-IP throttling (the current per-address bucket observes the immediate peer). Configure WAF/rate limits as needed. Test HTTP redirect, HTTPS, cookies, CSRF, logout, reset/invite delivery and deactivation behind the actual ALB.
8. Run release checks, application/image/secret scans, restore drill and staff UAT. Current image scan/CI status must be reported, not inferred from workflow files.

## Rollout and CI/CD

`checks.yml`: release-gate unit tests; exact Python and PostgreSQL; hash installs, checks/migration drift, migrations, domain+concurrency tests, browser journey, pip audit, deployment checks, vendor hashes, production image build/Trivy and Gitleaks. It also runs application tests inside the installer-free production image, verifies pip/ensurepip removal, and retains a development target for pip-based tooling. Workflow files are prepared; GitHub-hosted run results are unverified until pushed and executed. Review/pin third-party action commits according to repository policy before production.

`deploy.yml` is manual, protected by a GitHub `production` environment. Configure required reviewers and branch restrictions. Before requesting AWS credentials, it queries GitHub for the exact checked-out SHA and requires its latest trusted push Checks run to have completed successfully. An earlier success cannot override a later failure/pending run. Fork, pull-request-only and unrelated-workflow runs cannot authorize deployment. Eleven unit tests cover this gate; the authenticated GitHub API path still requires an actual hosted workflow run. The backup/migration plan remains a human approval enforced by environment reviewers. AWS OIDC role trust must restrict repository/environment. No static AWS keys in GitHub. Set repository/environment variables corresponding to the renderer's placeholders plus AWS_DEPLOY_ROLE_ARN, ECR_REPOSITORY, ECS_CLUSTER, ECS_SERVICE.

Build the `production` target and scan the immutable commit, push to ECR with immutable tags and scanning enabled. Prefer digest references for final task registration; the provided pipeline tags full Git SHAs and requires ECR tag immutability. Do not register/deploy the task until the RDS CA, Region, networking, SMTP, DB role and cost gates are complete.

Migrations are **not** executed by app startup. Before an update: take/verify backup; inspect `migrate --plan` and SQL; choose an additive backward-compatible migration; run `python manage.py migrate --noinput` as a controlled one-off ECS task using the new image and migration role; wait for successful exit. Only then approve the deployment workflow. Destructive changes require a separately reviewed expand/contract plan and tested restoration. Roll back app to previous task only when schema compatibility is confirmed; never blindly reverse database migrations.

Bootstrap administrator with the interactive management command from a controlled deployment shell/exec session. No first-login privilege assignment. Replace DB/backend containers and verify records plus a previously authenticated session persist. Set alerts for health failures, 5xx, DB storage/connections, CPU/memory, failed backups and suspicious login activity. Avoid request bodies/secret values in logs. Retain audit records under approved retention/access rules.
